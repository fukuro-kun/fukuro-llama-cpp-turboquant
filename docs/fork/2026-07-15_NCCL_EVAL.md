# #79 NCCL Communication Optimization — Evaluation Report

**Datum:** 2026-07-15 | **ROADMAP Item:** #79 | **Status:** ✅ Evaluiert — NCCL bereits integriert und working

---

## Zusammenfassung

**NCCL ist bereits im Fork integriert und funktionsfähig.** Der Build auf Uranus hat `GGML_CUDA_NCCL=ON` und NCCL 2.30.7 ist installiert. NCCL wird auf Linux automatisch als Default-AllReduce-Methode für Tensor Parallelism verwendet.

**Key Findings:**
1. **NCCL vs Internal AllReduce:** NCCL ist +4-8% schneller für Prompt Processing (pp), aber -3-6% langsamer für Token Generation (tg) auf PCIe-only Setups (kein NVLink)
2. **Tensor Parallelism vs Layer Split:** TP gibt +23-32% tg Speedup, aber -11-21% pp Regression
3. **12B-Modell crasht mit TP** (Meta-Backend Split-Assertion), 26B und E4B funktionieren
4. **Empfehlung:** Für tg-heavy Workloads auf Uranus: `GGML_CUDA_ALLREDUCE=internal` + `-sm tensor`

## Analyse

### NCCL vs Internal AllReduce

| Metrik | NCCL | Internal | Vorteil |
|--------|------|----------|---------|
| pp512 (E4B) | 3958 | 3672 | NCCL +7.8% |
| pp512 (26B) | 2677 | 2572 | NCCL +4.1% |
| tg128 (E4B) | 110.5 | 114.5 | Internal +3.6% |
| tg128 (26B) | 85.4 | 88.5 | Internal +3.6% |

**Erklärung:**
- **NCCL ist optimiert für große Tensoren** (pp mit 512 Tokens → große AllReduce-Operationen). NCCL verwendet optimierte CUDA-Kernel für kollektive Operationen.
- **Internal AllReduce (Butterfly) ist optimiert für kleine Tensoren** (tg mit 1 Token → kleine AllReduce-Operationen). Der Butterfly-Algorithmus hat weniger Overhead bei kleinen Datenmengen.
- **Auf PCIe-only Setups (kein NVLink)** ist der Internal-Algorithmus für tg leicht überlegen, da NCCL's Topologie-Erkennung für PCIe suboptimal sein kann.

### Tensor Parallelism vs Layer Split

| Metrik | Layer Split | Tensor Parallel | Vorteil |
|--------|-------------|-----------------|---------|
| pp512 | Besser (pipelined) | Schlechter (AllReduce-Overhead) | Layer Split +11-21% |
| tg128 | Schlechter (sequential) | Besser (doubled compute) | TP +23-32% |

**Erklärung:**
- **Layer Split** pipelined die Berechnung: GPU 0 berechnet Layer N während GPU 1 Layer N-1 verarbeitet. Bei großen Batches (pp) ist dies effizienter als TP's AllReduce-Overhead.
- **Tensor Parallelism** splittet jede Layer's Tensoren über beide GPUs. Bei kleinen Batches (tg, 1 Token) verdoppelt sich die Compute-Power, während der AllReduce-Overhead relativ klein ist.

| E4B (dense) | ✅ | Alle Tensoren können gesplittet werden |

## Empfehlung

### Für Uranus Produktionsserver (E4B + MTP)

**Aktuelle Konfiguration:** Layer Split + MTP
**Optimale tg-Konfiguration:** TP + Internal AllReduce + MTP

**Optionale Optimierung:**
```bash
GGML_CUDA_ALLREDUCE=internal ./llama-server -m model.gguf -sm tensor -ngl 99 -fa 1 ...
```

**Caveat:** MTP + TP muss noch verifiziert werden. MTP verwendet einen Draft-Model, der möglicherweise nicht mit TP kompatibel ist.

### AllReduce-Methoden-Selektor

Die Environment-Variable `GGML_CUDA_ALLREDUCE` steuert die Methode:
- `nccl` (Default auf Linux): Beste für pp-heavy Workloads
- `internal`: Beste für tg-heavy Workloads auf PCIe-only Setups
- `auto`: Automatische Auswahl (noch nicht implementiert)

**Zukünftige Verbesserung:** Ein automatischer Selektor basierend auf Batch-Größe wäre ideal — NCCL für pp (große Batches), Internal für tg (kleine Batches). Dies erfordert jedoch eine tiefere Integration in den Scheduler.
